# Phase 10: スリープ阻害の解消（キャプチャストリームの保持をやめる）

## 目的

本アプリを常駐させると Windows がスリープに入らなくなる問題（Issue #1）を解消する。
キャプチャストリームを開きっぱなしにしない設計へ変更する。

## 背景

Issue #1 の実測で、原因は以下と特定済み。

- アプリ自身は `SetThreadExecutionState` を呼んでいない
- WASAPI のキャプチャストリームを開きっぱなしにしているため、USB オーディオ
  ドライバ側が Windows に SYSTEM 電源要求を立てている
- `powercfg /requests` にはプロセスではなく `[DRIVER] USB Audio Device` として現れる
- Phase 9 の `resolve_input_device()` 導入で掴む対象がオンボードから USB 受信機へ
  変わったことが、症状の出はじめた契機

該当箇所:

- `main.py` `run()` — 起動時に無条件で `start()`、以降は手動トグルか終了まで閉じない
- `monitor.py` `_monitor_loop()` — 自動一時停止は `_paused = True` にするだけで
  ストリームは開いたまま。アラート音は止まるが電源要求は残る

## スコープ

対象: `activity.py`（新規）, `main.py`, `tray.py`, `gui.py`, `settings.py`

スコープ外:
- `monitor.py`（`start()` / `stop()` をそのまま使う。検出ロジックは触らない）
- `notifier.py`, `build.spec`（変更不要）
- Issue #1 の案3（不採用）・案4（アプリ外の回避策）

## 採用方針

**案1（PC の無操作時間で監視を自動停止／再開）を本命として実装し、案2（他アプリが
マイク使用中は監視を継続）を上乗せする。** PO 指示による。

### 判定式

```
suspend = idle_suspend_enabled
          and not (mic_share_monitor_enabled and 他アプリがマイク使用中)
          and 無操作秒数 >= しきい値
```

他アプリがマイクを掴んでいる間は、そちら由来で電源要求が立つ。こちらが閉じても
どのみちスリープしないため、監視を続けた方が得になる。これが案2の根拠。

## 主な決定事項

**しきい値は設定項目にする（既定 180 秒）。** 全体設計は「ユーザーが調整しなくてよい
パラメータは設定項目にしない」方針だが、この値は各環境の Windows スリープ設定より
短くなければ機能しない。内部定数では環境によって効かないため例外とする。

**自動停止／再開では通知音を鳴らさない。** 手動トグルと区別するため、`_toggle_monitor()`
を経由せず `AudioMonitor.start()` / `stop()` を直接呼ぶ。

**「ユーザーが監視を望んでいるか」の意図を明示的に保持する。** これがないと、手動で
監視を停止したのに操作再開で勝手に復活する。`_monitor_desired` として持ち、自動制御は
これが True のときだけ働く。

**トレイに `suspended` 状態を追加する。** 自動停止中は `is_running` が False になるため、
これがないと手動停止と見分けがつかない。

**GUI の監視ボタンはポーリングで追随させる。** 現状 `gui.py` はトグル時にしかラベルを
更新しておらず、自動停止すると表示が実態とずれる。500ms の既存ポーリングに寄せる。

**スリープ復帰は再開失敗のリトライで吸収する。** `WM_POWERBROADCAST` の購読には
ウィンドウメッセージループが要る。復帰後はユーザーが必ず操作するため無操作秒数が
下がり、再開が走る。その際の `start()` 失敗はダイアログを出さず次の巡回で開き直す。

**案2 は自プロセスを除外する。** ConsentStore には自分自身も載る。除外しないと
「自分が掴んでいる ＝ 他アプリ使用中」となり永久にストリームを閉じない。

**案2 は ConsentStore の記録をそのまま信じない（実装中に判明）。** アプリが停止時刻を
書かずに終了すると `LastUsedTimeStop` は 0 のまま残り、恒久的に「使用中」を返す。
実機の確認で、アンインストール済みの旧バージョンの Discord が3件、最終開始時刻が
2023-12 / 2025-10 / 2026-02 のまま「使用中」として残っていた。

| エントリ | 最終開始 | 実体 | 判定 |
|---|---|---|---|
| Discord app-1.0.9027 | 2023-12-19 | なし | 残骸 |
| Discord app-1.0.9212 | 2025-10-29 | なし | 残骸 |
| Discord app-1.0.9223 | 2026-02-14 | なし | 残骸 |
| Discord app-1.0.9252 | 2026-08-17 | あり・稼働中 | 有効 |

これを信じると `other_app_using_mic()` が常に True となり、**案2 が案1 を完全に無効化して
スリープ阻害が全く解消しない**。実行ファイルが実在すること、かつ同名のプロセスが
稼働していることの両方を条件に加える。

**曖昧なときは「使用中でない」に倒す。** 誤って False にしても、無操作時に監視を止める
という本来の動作になるだけで実害がない。逆に誤って True にすると機能そのものが死ぬ。
この非対称性から、ストアアプリ（実行ファイルのパスが分からず生存確認できない）は
案2 の対象外とする。想定用途の Discord・OBS・Zoom はいずれも Win32 アプリ。

## 併せて対応する PO 要望（Issue #1 スコープ外）

| 項目 | 対応 |
|---|---|
| 既定設定の更新 | 実機 `config.json` に合わせ `alert_interval_sec` を 30 → 10 |
| バージョン表示 | `version.py` を新設し、設定画面のフッタと詳細設定タブに表示 |
| 設定ファイルへの導線 | トレイメニューに「設定ファイルの場所を開く」を追加 |
| トレイアイコン刷新 | 角丸スクエア＋グラデーション＋マイクのグリフに変更 |

**`device_index` は既定値にしない。** 実機の `config.json` には `12` が入っていたが、これは
その PC の PortAudio インデックスであり、別環境では別のデバイスを指すか存在しない。
`None` のとき `resolve_input_device()` が WASAPI の既定を選ぶ設計（Phase 9）が正しく働く。

**アイコンはキャッシュする。** 状態表示は 0.5 秒ごとに更新されるため、そのつど描き直すと
無駄が大きい。状態は5種類しかないので生成結果を保持し、状態が変わったときだけ差し替える。

## 副次的に修正した点

`詳細設定` タブはスクロールに対応しておらず、設定項目を追加するとサイズ固定の
ウィンドウに収まらなくなった。`通知設定` タブのスクロール実装を共通ヘルパーに
切り出して両タブで使う。

その際、既存実装がホイールを `bind_all` で全体に張っていたため、スクロール領域が
2つになると後から張った側が奪う状態だった。ホイールは1箇所で受け、イベントの
発生元から親を辿って対象のタブを決める方式に改める。

## 追加する設定項目

| キー | 既定 | 意味 |
|---|---|---|
| `idle_suspend_enabled` | `True` | 無操作での自動停止を行うか |
| `idle_suspend_sec` | `180` | 無操作と判定するまでの秒数（30〜1800） |
| `mic_share_monitor_enabled` | `True` | 他アプリがマイク使用中は監視を継続するか |

## テスト計画

自動テスト（`test_phase10.py` 27件 / `test_suspend_flow.py` 24件 / `test_gui_build.py` 18件）:

- 無操作秒数: `GetLastInputInfo` が操作直後に 0 付近を返すこと
- 32bit 周回: `GetTickCount` の巻き戻りで負値や巨大値にならないこと
- 自プロセス除外: 自身がマイクを開いていても「他アプリ使用中」と判定しないこと
- stale 除外: 実体が消えた／プロセスが居ないエントリを使用中と見なさないこと
- 判定関数: 無効時 / 他アプリ使用中 / しきい値未満 / 超過 / 境界値 の分岐
- 自動停止: しきい値経過でストリームが閉じ、通知音が鳴らないこと
- 自動再開: 操作再開でストリームが開き、通知音が鳴らないこと
- 重複防止: 停止中に stop、再開済みに start を重ねて呼ばないこと
- 手動停止の尊重: 手動停止後、操作を再開しても監視が復活しないこと
- 再開失敗: 失敗時は自動停止状態を維持し、次の巡回で再試行すること
- デバイス変更: 自動停止中に設定を変えてもストリームを開き直さないこと
- 表示追随: 自動停止中にボタン・ステータスが手動停止と区別されること
- 設定の保存とクランプ（30〜1800秒）
- アイコン: 全状態が 64x64 RGBA・状態ごとに異なる・キャッシュが効くこと

実機確認（PO 実施）:

- `powercfg /requests` の SYSTEM から `[DRIVER] USB Audio Device` が消えること
- 放置して Windows が実際にスリープに入ること
- スリープ復帰後に監視が再開すること
- 送信機OFFでのアラートが従来どおり鳴ること（回帰確認）

## 既知の制約

- Discord など他アプリがマイクを掴んでいる間は、案2 により監視を継続する。この間は
  そのアプリ由来で電源要求が立つためスリープしない。これは設計どおりの挙動で、
  「他アプリ使用中は継続」をオフにすれば監視側は止まる（ただしスリープするかは
  そのアプリ次第）
- ストアアプリのマイク使用は検出しない（生存確認ができないため）
- Issue #1 補足の「レガシー カーネルの呼び出し元」は別系統の要因で、本件の修正では
  解消しない
